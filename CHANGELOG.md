# Changelog

Notable changes to `@ravitecnologia/kstonebase-mcp`. Versions before 2.2.0 are described in the git history.

## Unreleased

### Added

- Engineering write and action tools (Kstonebase MCP spec `features/mcp-engineering-tools.md` MT-I12–MT-I14, PBI 239), after the 20 engineering reads, in this order: `link_engineering_evidence` (ADDITIVE), `unlink_engineering_evidence` (OVERWRITE; `DELETE …/links/:linkId?expectedVersion=n`), `save_board_item_assessment` (ADDITIVE), `propose_engineering_action` (ADDITIVE), `read_engineering_action` (READ), `list_engineering_actions` (READ) and `cancel_engineering_action` (OVERWRITE). They come from the shared `src/engineering-catalog.ts` (new `ENGINEERING_ADDITIVE` / `ENGINEERING_OVERWRITE` annotations, `ENGINEERING_WRITE_TOOLS`); the snapshot now pins 27 entries.
- The five writes end with the optional `expectedPolicyRevision`, sent only as the `X-Kstonebase-Policy-Revision` header; the reads never send it. `EngineeringRequest` gains `DELETE`, `write` and `policyRevision`; `KstonebaseClient.engineeringRequest(method, mcpPath, body?, { write, policyRevision })`.
- `propose_engineering_action.input` is a union of six strict shapes (`pull_request.create|update|request_review|merge`, `pipeline.run`, `board.complete`), checked locally against `kind` (`VALIDATION_ERROR {field: "input", problem: "invalid-value"}`, no request). A successful proposal adds a second text item: "Proposed only. Nothing was changed in <GitHub|Azure DevOps> (`board.complete`: No card was moved). A person must review and confirm it in Kstonebase: <configured Kstonebase URL><reviewUrl>. Confirmation expires at <expiresAt>." A replayed proposal that is no longer proposed says so instead.
- Refusals: `ACTION_CONFLICT`, `ACTION_STATE_CONFLICT`, `ACTION_ACTOR_REQUIRED`, `ACTION_NOT_FOUND`, `ACTION_STALE`, `ACTION_EXPIRED`, `HUMAN_CONFIRMATION_REQUIRED`, `STALE_VERSION`, `IDEMPOTENCY_KEY_REUSED`, `LINK_LIMIT_REACHED`, `LINK_NOT_FOUND`, `ARTIFACT_NOT_FOUND`, `DEPLOYMENT_NOT_FOUND`, `ASSESSMENT_NOT_FOUND`, `ITEM_ARCHIVED`, `COMPLETION_NOT_ELIGIBLE`, `PULL_REQUEST_EXISTS`, `PULL_REQUEST_NOT_OPEN`, `PULL_REQUEST_DRAFT`, `PULL_REQUEST_NOT_MERGEABLE` and `INVALID_REFERENCE` are engineering tool codes with catalog remediations; the detail allowlist adds `limit`, `actionId`, `state`, `itemId`, `number` and `verdict`. Error mode "engineering-write": a write that fails in flight (or with an unexpected API error) is `INTERNAL_ERROR` saying the change may or may not have been applied and to read the current state before retrying with the same `idempotencyKey`; reads keep their text.
- `init_workspace` / `init_product` list the two new reads as reads and the five writes as writes (the evidence and assessment-save writes for Workspace bindings only); README documents the write tools and the confirmation rule; the ChatGPT app manifest declares the new tools. Package version 2.8.0.

**Requires** a Kstonebase deployment whose Website proxies `POST`/`DELETE` engineering links, the assessment save and the action routes under `/api/mcp/…`; `board.complete` proposals also need an API with guarded completion. Against an older deployment the new tools answer `ENGINEERING_UNSUPPORTED`.

- Engineering discovery, read and assessment tools (Kstonebase MCP spec `features/mcp-engineering-tools.md` ME1–ME8, PBI 230; backed by the API's `/mcp/products/:productId/engineering…`, `/mcp/products/:productId/delivery-config/effective`, `/mcp/workspaces/:workspaceId/engineering/repositories`, `/mcp/workspaces/:workspaceId/delivery-policy` and `/mcp/workspaces/:workspaceId/board…/engineering…` routes): `get_engineering_capabilities`, `list_engineering_repositories`, `read_delivery_configuration`, `read_workspace_delivery_policy`, `resolve_revision`, `read_repository_tree`, `read_repository_file`, `search_repository_code`, `compare_revisions`, `list_commits`, `list_pull_requests`, `read_pull_request`, `read_revision_checks`, `list_ci_runs`, `read_ci_run`, `list_deployments`, `read_active_deployment`, `list_engineering_links`, `discover_engineering_links` and `assess_board_items`, on both transports, after the existing tools. All are read-only (`readOnlyHint: true`, `idempotentHint: true`; `openWorldHint: true` for the provider reads) and carry no `expectedPolicyRevision`; `assess_board_items` is a POST that changes nothing on the Board.
- Their names, titles, descriptions, annotations, input schemas and API requests come from `src/engineering-catalog.ts`, a file shared verbatim with the Kstonebase-hosted and Desktop session registry; `src/engineering-catalog.snapshot.json` pins the rendered `tools/list` entries and both repositories test against the same file.
- Workspace tools use the passed `workspaceId`, else the bound one, else `WORKSPACE_NOT_BOUND`; Product tools need an explicit `productId`. Results are the API bodies, unchanged, with the Workspace instructions notice of the addressed Product or Workspace.
- Error mode "engineering": the API's `details.code` is the tool code (`ENGINEERING_UNAVAILABLE`, `ENGINEERING_DELEGATION_REQUIRED`, `ENGINEERING_CONSENT_REQUIRED`, `PROVIDER_CONSENT_REQUIRED`, `PROVIDER_PERMISSION_INSUFFICIENT`, `NOT_ALLOWED_BY_POLICY`, `PROVIDER_FEATURE_UNSUPPORTED`, `PROVIDER_RATE_LIMITED`, `PROVIDER_UNAVAILABLE`, `REPOSITORY_NOT_CONFIGURED`, `DELIVERY_NOT_CONFIGURED`, `REPOSITORY_CHANGED`, `REPOSITORY_ACCESS_DENIED`, `CONNECTION_REQUIRED`, `REVISION_NOT_FOUND`, `PATH_NOT_FOUND`, `PULL_REQUEST_NOT_FOUND`, `CI_RUN_NOT_FOUND`, `ENVIRONMENT_NOT_FOUND`, `STAGE_NOT_FOUND`, `PRODUCT_NOT_FOUND`, `PRODUCT_ARCHIVED`, plus the shared credential, Board and validation codes) with the catalog remediation and the allowlisted details `field`, `problem`, `currentVersion`, `retryAfter`, `operation`, `provider`, `remediation`, `feature`, `changed`, `hint`. A 404 without any Kstonebase error code (an older deployment) is `ENGINEERING_UNSUPPORTED`: nothing was verified.
- `KstonebaseClient.engineeringRequest(method, mcpPath, body?)`; `init_workspace` / `init_product` list the engineering reads; README documents them; the ChatGPT app manifest declares them.

**Requires** a Kstonebase deployment whose API serves the engineering routes (API 1.18 or later) and whose Website proxies them under `/api/mcp/…`, and a token with engineering access. Against an older deployment the new tools answer `ENGINEERING_UNSUPPORTED` and every other tool keeps working.

- Effective Workspace instructions (Kstonebase MCP spec `features/workspace-agent-instructions.md`, frozen contract PBI 176, backed by the API resolver behind the Website's `/api/mcp/agent-policy`): new read tool `get_effective_instructions` (`workspaceId`, `productId` or `specificationId`, at most one; the binding's `productId`, then `workspaceId`, is the default) returning `{ target, policy }` with the API's validated policy (schemaVersion 1; text only in Workspace mode). Errors: `POLICY_TARGET_REQUIRED` (nothing to resolve), `VALIDATION_ERROR` (two or more ids), `NOT_FOUND` / `TOKEN_SCOPE_MISMATCH` (per item) and `POLICY_UNSUPPORTED` (a server without the resolver: a 404 without a JSON error code, or a non-JSON body).
- Every successful result of a tool that addresses a Workspace, Product or specification ends with one extra text item, the Workspace instructions notice (Workspace mode with the verified text, Local mode, `unavailable: <reason>`, or the multi-scope notice for `list_products` without a Workspace), built from a fresh resolver call for that call, plus `_meta["kstonebase.com/policy"]`. Existing content items and `structuredContent` are unchanged; failed results, `list_workspaces`, `init_workspace`, `init_product` and the `kstonebase://` resources get no notice. The text is cached in memory by `policyRevision` and requested with `instructions=omit` once known; the revision is resolved on every call.
- Every API write tool accepts an optional `expectedPolicyRevision` (`^wp1_[A-Za-z0-9_-]{22}$`), sent only as the `X-Kstonebase-Policy-Revision` header and never in the body; without it no header is sent. New error codes `POLICY_STALE`, `POLICY_REVISION_REQUIRED` and `INVALID_POLICY_REVISION` (mapped from `details.code` in every mode, Board tools included) tell the agent to resolve again and ask the user, never to replay.
- The MCP `initialize` answer carries the contract's server `instructions` on stdio and `--http` alike. `init_workspace` / `init_product` list `get_effective_instructions` in the generated CLAUDE.md / AGENTS.md; README documents the notice, the revision precondition and that external agents remain responsible for following the instructions.
- `KstonebaseClient.getAgentPolicy(targets, { omitInstructions })`, and an optional last `WriteOptions` argument (`{ policyRevision }`) on every write method.

**Requires** a Kstonebase deployment whose API serves the agent-policy resolver and whose Website proxies `/api/mcp/agent-policy` and forwards `X-Kstonebase-Policy-Revision`. Against an older deployment every tool keeps working, scoped results carry an `unavailable: unsupported` notice and `get_effective_instructions` answers `POLICY_UNSUPPORTED`.

- Native Board tools for Software Engineering Workspaces (Kstonebase MCP spec `features/mcp-board-tools.md` §2.1, backed by the API's `/mcp/workspaces/:workspaceId/board…` routes): `read_board`, `list_board_items`, `read_board_item`, `list_board_item_notes`, `create_board_item`, `update_board_item`, `link_board_specification`, `unlink_board_specification`, `append_board_item_note`, `archive_board_item` and `restore_board_item`, on both the stdio and `--http` transports. Names, titles, descriptions, annotations (all with `idempotentHint: true`) and input schemas match the Kstonebase-hosted endpoint; results are the API bodies, unchanged.
- Board tools target only a Workspace: the passed `workspaceId`, else the `.kstonebase.json` `workspaceId`, else `WORKSPACE_NOT_BOUND` before any request. A bound `productId` is never used, so it cannot narrow or widen Board access; Product-restricted credentials get the API's `WORKSPACE_SCOPE_REQUIRED` with its hint.
- `create_board_item` and `append_board_item_note` require an `idempotencyKey`, forwarded exactly as given; the package never generates, swaps or retries keys. A Board request that fails in flight reports `INTERNAL_ERROR` telling the agent to re-read and to retry only with the same key.
- `KstonebaseClient` Board methods (`readBoard`, `listBoardItems`, `readBoardItem`, `listBoardItemNotes`, `createBoardItem`, `updateBoardItem`, `linkBoardSpecification`, `unlinkBoardSpecification` — DELETE with a JSON `{expectedVersion}` body — `appendBoardItemNote`, `archiveBoardItem`, `restoreBoardItem`). PATCH bodies carry only the fields given; explicit `null` clears `assigneeId` / `productId`.
- Error codes `BOARD_UNAVAILABLE`, `ITEM_NOT_FOUND`, `WORKSPACE_ARCHIVED`, `OWNER_REQUIRED`, `INVALID_PARENT`, `INVALID_ASSIGNEE`, `INVALID_PRODUCT`, `INVALID_CURSOR`, `IDEMPOTENCY_KEY_REUSED`, `ACTIVE_CHILDREN`, `PARENT_ARCHIVED`, `ITEM_ARCHIVED`, `ITEM_NOT_ARCHIVED`, `SPECIFICATION_UNAVAILABLE`, `SPECIFICATION_ARCHIVED` and `LINK_LIMIT_REACHED`. For Board tools the API's `details.code` is the tool code — credential refusals included (`WORKSPACE_SCOPE_REQUIRED`, `TOKEN_SCOPE_MISMATCH`, `TOKEN_SCOPE_INSUFFICIENT`) — and the details `field`, `problem`, `currentVersion`, `activeChildren`, `limit` and `hint` are passed on. `STALE_VERSION` carries `currentVersion` and tells the agent to re-read and reconcile, never to replay. A Board route that answers without any error code (an older deployment) is explained as missing server support. Error codes and details of every other tool are unchanged.
- `init_workspace` and `init_product` list the Board tools in the generated CLAUDE.md / AGENTS.md for Workspace bindings. README documents the native Board workflow; the ChatGPT app manifest declares the new tools.
- Board import report reads (Kstonebase MCP spec `features/mcp-board-tools.md` §2.2, backed by the API's `/mcp/workspaces/:workspaceId/board/imports…` routes): `list_board_imports` (`limit`, `cursor` → `RunPage`) and `read_board_import` (`importId`, `limit`, `cursor`, `plan`, `outcome` → `RunDetail`), with the contract's titles, descriptions and Board READ annotations, on both transports. They target the Workspace exactly like the other Board tools (passed or bound `workspaceId`, never `productId`), are Workspace-Owner-only and return the API bodies unchanged; reports never contain a credential. No tool connects an Azure DevOps source, runs discovery, changes a mapping or confirms, cancels or retries an import — that stays a human step in the Website (Workspace Settings → General → Azure DevOps, and Import from Azure DevOps on the Board).
- `KstonebaseClient.listBoardImports` and `readBoardImport` (query `limit`, `cursor`, `plan`, `outcome`; an empty, `.` or `..` `importId` is refused before any request).
- Error code `IMPORT_NOT_FOUND`. For the import report tools `OWNER_REQUIRED` explains that reports are Workspace-Owner-only while Members can still read imported cards, `INVALID_CURSOR` / `VALIDATION_ERROR` name the report arguments, and a code-less 404/405/501 is explained as a deployment without the import report routes.
- `list_board_items` and `read_board_item` pass through the API's new `origin` field unchanged — the immutable Azure DevOps provenance of an imported card, `null` for native cards. `create_board_item` and `update_board_item` never forward an `origin` argument.

**Requires** a Kstonebase deployment whose API serves the native Board and whose Website proxies `/api/mcp/workspaces/:workspaceId/board…`; the import report tools also need the API's `…/board/imports` MCP routes.

### Changed

- `request_review` no longer describes an open-question gate: Kstonebase accepts review requests, and Owners approve versions, while open questions remain (Kstonebase Business PDR-0007, changed 2026-09-26). The tool still maps `OPEN_QUESTIONS_PRESENT` from older servers.
- `update_open_question` describes answering after review: resolving an `OPEN` question with its answer (and no `body` or `sectionPath`) also works on a specification in Needs Review or Reviewed, and the Kstonebase API moves it to Draft in the same change — back to Draft at the same version from Needs Review, a new draft from Reviewed — so agents answer directly instead of calling `start_new_version` first (Kstonebase MCP spec `features/mcp-open-question-management.md` §11). The `SPEC_LOCKED` remediations for Reviewed and Needs Review specs name this exception. The description is byte-identical to the Kstonebase-hosted MCP endpoint's. Older servers still refuse such answers with `SPEC_LOCKED`.
- `update_open_question` also describes accepting (`RESOLVED`) or rejecting (`DISMISSED`) an `OPEN` assumption after review: with no `body` or `sectionPath` it works on a specification in Needs Review or Reviewed, and the Kstonebase API moves it to Draft in the same change, exactly like an answer (Kstonebase MCP spec `features/mcp-open-question-management.md`, decision of 2026-09-26 on assumptions). The `SPEC_LOCKED` remediations name both exceptions. Dismissing a question stays Draft-only. Older servers refuse these changes with `SPEC_LOCKED`.

### Fixed

- The server reports its package version again in `serverInfo` (it still said 2.2.0).

## 2.2.0

Additive release: agents can manage a specification's open questions and assumptions (Kstonebase MCP spec `features/mcp-open-question-management.md`).

**Requires** a Kstonebase deployment whose API serves the open-question routes and whose Website proxies them under `/api/mcp/specifications/:specId/open-questions` (GET, POST) and `/api/mcp/specifications/:specId/open-questions/:questionId` (GET, PATCH, and DELETE with a JSON body). Against an older deployment the four new tools fail; `list_open_questions` keeps working.

### Added

- `read_open_question`, `create_open_question`, `update_open_question` and `delete_open_question` on both the stdio and `--http` transports, with the schemas, descriptions and annotations pinned by the shared open-question contract. Changes need a non-archived Draft and the spec `version`; updates and deletes also need the item's `updatedAt` as `expectedUpdatedAt`. The API changes the record and its Markdown marker together. `delete_open_question` is permanent; dismissing keeps the item and can be undone by reopening.
- `KstonebaseClient` methods `readOpenQuestion`, `createOpenQuestion`, `updateOpenQuestion` and `deleteOpenQuestion` (DELETE sends a JSON body). Tokens are sent exactly as given, undefined keys are omitted and explicit `null`s are kept; empty, `.` and `..` ids are rejected before any request.
- Error codes `STALE_QUESTION`, `MARKER_NOT_FOUND`, `MARKER_AMBIGUOUS`, `SECTION_AMBIGUOUS`, `ANSWER_REQUIRED`, `INVALID_TRANSITION` and `SPEC_ARCHIVED`, each with a remediation that asks the agent to re-read instead of retrying blindly. A missing section — an unknown `sectionPath`, or a reopen whose recorded heading no longer exists — is reported as `NOT_FOUND`, as on the Kstonebase-hosted MCP endpoint; its remediation and the `sectionPath` / `reason` / `hint` details say which case it is.
- Tool failures carry the API's actionable `details` (`hint`, `reason`, `fields`, `status`, `sectionPath`, `from`, `to`), in the structured result and in the text.
- `init_workspace` and `init_product` list the new tools in the generated CLAUDE.md / AGENTS.md.

### Changed

- `list_open_questions` passes through the additive `spec` metadata and the `specificationId` / `resolvedAt` item fields when the API returns them. Its arguments and default filtering are unchanged.
- For specification and question codes, error mapping reads the specific `error.details.code` before the generic envelope code. This fixes codes that were reported wrongly: `OPEN_QUESTIONS_PRESENT` and `PRODUCT_TYPE_MISMATCH` (were `INTERNAL_ERROR`), archived specs (were `TOKEN_SCOPE_MISMATCH`, now `SPEC_ARCHIVED`) and rejected lifecycle transitions (were `INTERNAL_ERROR`, now `INVALID_TRANSITION`). Credential, scope and binding failures keep their existing codes: a token without the `write` scope, for example, still reports `TOKEN_SCOPE_MISMATCH`, with `TOKEN_SCOPE_INSUFFICIENT` as the message.
- The `SPEC_LOCKED` remediation follows the spec status and no longer suggests `start_new_version` for a spec in Needs Review. The `STALE_VERSION`, `OPEN_QUESTIONS_PRESENT`, `NOT_FOUND`, `VALIDATION_ERROR` and `INTERNAL_ERROR` remediations were reworded; writes are never retried automatically.
- The MCP `serverInfo.version` now reports the package version (it said 2.0.0).
